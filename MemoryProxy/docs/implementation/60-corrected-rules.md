## 1 术语（本单第一产出；三词各自：定义 + 依据 + 边界/反例）

### 1.1 `corrected`（定义）

**对既有 `asset_used` 归因的机器修正事件**：表示"该使用归因所依据的证据面发生了**后续**变化
（版本 / 提取绑定 / 可回查性），机器据此**对既有归因打修正标记**"。

- **依据**：`review :104`（状态机词汇，与 used/validated 并列）+ `00:47`（"对齐设计文档状态机"）
  + `10:49`（"corrected **规则**"是消费端）+ `30:58`（"被 corrected 时**撤销**"——修正会级联）。
- **边界/反例**（写死，防越界）：
  - **corrected ≠ 重判**：重判（61 `round>0`）= 产生**新 judgement 行**；corrected **不产生新判定**、
    **不回改 used 行**、**不改 verdict**。反例：把 corrected 实现成"自动把 used 改成 refuted"
    ⇒ 越界（判定变更只能走重判路径）。
  - **corrected ≠ 人工修正**：S7 展示层的人工修正不属"机器规则"（本 spec 只定义机器面；
    人工面随 S7）。
  - **corrected 必须有可指名的机器证据**（三路见 §2）；无证据的"怀疑"不产事件（62 的"不猜"纪律）。

### 1.2 "三路"（**已裁定**：按推荐口径采纳，见勘正 3；依据/反例/备选保留供复核）

**推荐口径（本文按此展开）："三路" = `corrected` 的三类机器触发源** ——
**L1 版本漂移 / L2 提取绑定撤销 / L3 回查失效**。

- **依据**（按硬度）：L2 有**原话实锤**（`30:57-59`"……记来源 asset_id、**被 corrected 时撤销**"）；
  L1 有**并列证据**（roadmap 同格"corrected + 版本链快照" + `15:31/:342`"版本漂移/正文变化快照
  随 S6" + 58/DR-6a 的锚版实测）；L3 有**契约面**（`00:49-52`"必须能被现有 client 回查" +
  `10:49`"v2 消费端要拿 `asset_id` 经…回查"）。
- **反例检验**（排除其它读法）：
  - "三路 = 三种资产状态（used/validated/corrected）"——**不通**：那是三个**词**，不是"三路**规则**"；
  - "三路 = 三个数据源（档①/档②/事件表）"——无档源支持，且与"机器规则"语序不合；
  - "三路 = 三种修正动作（改判/撤销/降级）"——与 §1.1 的"不改 verdict"边界冲突，且无档源。
- **备选口径（若人裁不同）**：第三路可改为"**引文排他性复核**"（57 度量复算）——但复核产新判定
  ⇒ 与重判重叠 ⇒ **不推荐**。**切换成本**：替换 §2.3 + §7 对应 golden（改动局限两节）。
- **裁定时点建议**：S6 实现单开工前（本文其余部分按推荐口径自洽，任一裁定均可局部替换）。

### 1.3 版本链快照（定义）

**同一 `(asset_id, session_key)` 在归档窗口内出现过的资产版本序列**
（每项：`version`（有则带，不伪造）+ 首见锚（引用 fetched 行 / 档①档② piece）+ 正文哈希（可得时））。

- **依据**：`15:31/:342`（"为版本漂移/正文变化做快照"、"随 S6 一起设计、**不在注入侧堆字段**"）
  + `15:21/:69`（清单条目"版本有则带"）+ F7（锚版 = 归档窗口）+ **F9**（fetched 行 payload 实带
  `version` ⇒ 数据源 = 既有行，**不需要新增注入侧字段**——与 15:342 的承诺完全不冲突）。
- **边界/反例**：
  - 版本号缺失（`15:69`"有则带"）⇒ 快照条目 `version: null`，但**仍记**首见锚与正文哈希
    （序与内容可得）；**不许伪造版本号**、**不许用递增猜测冒充**。
  - 窗口外版本**不出现**（DR-6a"不得回查当前资产存储"）⇒ 快照 = 窗口内快照，**不许回查补齐**。

## 2 `corrected` 三路机器规则

> 公共面（三路共用，写死）：
> - **输出事件**：`attribution_status_events` 一行，`event_type = "asset_corrected"`（写口见 §5）；
> - **幂等**：（unit_id, asset_id, round, event_type, route）唯一（见 §5 的派生主键勘正）；
> - **不回改**：used 行 / judgement 行零改写（不可变纪律，照 59/61）；
> - **写/不写都可观测**：每路分桶计数（照 62 的 `tombstoned`/`overflowed` 姿势）。

### 2.1 L1 · 版本漂移（推荐主路）

- **输入证据**：版本链快照（§3）中该 asset 在**同一归档窗口**出现 **≥2 个版本**，且既有
  used 行**锚定的版本 < 窗口内最新版本**（锚定版本从 fetched 行 `payload.version` / 档①档②
  归档取，**不回查当前存储**，F7）。
- **规则**（可机械化）：对每个满足条件的 used 行 ⇒ 产 1 条 `asset_corrected`
  （`route="version_drift"`，`anchored_version` / `latest_version` 落 payload）。
- **输出**：corrupted 事件行（**修正标记**，不改 used 行的任何列）。
- **golden**：注入 v1 →（同窗口）注入 v2 ⇒ 断言 1 条 corrected（anchored=v1、latest=v2）。
  **反例**：v2 仅出现在窗口**外** ⇒ **0 条**（DR-6a 口径）。

### 2.2 L2 · 提取绑定撤销（实锤路；实现随提取绑定落地）

- **输入证据**：某**来源资产**（instruction L1 等）被 L1 判出 corrected（版本漂移）或被 L3
  判出不可达；且存在**由该来源提取的绑定**（risk 词表种子等，`30:57` 的"提取绑定"）。
- **规则**（可机械化）：该来源的 corrected 事件 ⇒ **撤销其提取绑定**（`30:58` 原话）⇒
  对"由被撤销绑定支撑的既有归因"逐条产 `asset_corrected`（`route="binding_revoked"`，
  `source_asset_id` / `binding_ref` 落 payload）。
- **输出**：逐条 corrected 事件（同样**不回改**既有行）。
- **实现触发条件（后置登记）**：**提取绑定本身尚未落地**（`30:57-59`：v1 用内置种子词表常量、
  提取绑定"留 v2"）⇒ L2 的**实现单元 = 提取绑定落地那一单**（同批实现级联 + 其 golden）；
  **本 spec 先定语义与接口**。**反例**：内置种子词表（无来源资产）⇒ **不适用**（不得凭空撤销）。

### 2.3 L3 · 回查失效（保守路；消费端/离线触发）

- **输入证据**：used 行的 `asset_id` 经既有 client 回查（`00:52`：`meta/client` 的
  `list-accessible`（含 version）/ `knowledge/core-client`）得到**确定的"不存在/被拒"**
  （明确 404 / ACL 明确拒绝）。
- **规则**（保守，写死）：产 `asset_corrected`（`route="unreachable"`，`severity="signal"`）——
  **只标注、不改 verdict、不撤销**（"回查失败 ≠ 归因当时不存在"，证据弱）。
- **反例（必须不产）**：网络错误 / 超时 / 5xx / ACL 服务不可用 ⇒ **不产事件**（"不确定"≠"确定不存在"）；
  即：**只有确定性与否定性同时成立才产**。
- **触发时机**：**离线圈**（运维/审计显式发起的复核运行；自动化周期留后续登记，不在 S6 硬编码）。

### 2.4 `146` 裁定：L2 / L3 = **触发式登记**（本线不实现；**不得为凑数据放宽**）

- **L2 `binding_revoked`** —— **触发条件**：**提取绑定落地那一单**（同批实现级联 + 其 golden，§2.2）——
  提取绑定本身尚未落地（`30:57-59` 留 v2）⇒ 本线**无输入证据** ⇒ 触发式，不实现。
- **L3 `unreachable`** —— **触发条件**：**离线圈**（运维/审计显式发起的复核运行；自动化周期留后续登记，§2.3）；
  实现前提 = **确定性 ∧ 否定性**同时成立（明确 404 / ACL 明确拒绝）。
  **必不产清单（不得放宽）**：网络错误 / 超时 / 5xx / ACL 服务不可用 ⇒ **不产事件**（"不确定"≠"确定不存在"）；
- **共同保证**（与 L1 同批）：**只标注、不改 verdict、不撤销 `used`**；`route` 取值与白名单
  （`status-events-repo.ts`）**同批**改动 —— 本单（`146`）**零代码改动**、零新增事件。
- **禁令**：不得为让 L2/L3"有数据"而放宽上述任一条（尤其：不得把 5xx / 超时记成 `corrected`）——`R2` 钉。

## 3 版本链快照（形状 / 查询 / 幂等锚 / 落不落库）

- **形状（查询层重建，不物化——照 59/61 的既定纪律）**：从**既有数据**组装：
  ① fetched 行 `payload.version`（F9 实锤可得）；② 档①/档②归档 piece（首见锚 + 正文哈希）；
  ③ `attribution_events` 的 `created_at` / `rowid`（序）。**不新增注入侧字段**（`15:342` 承诺）。
- **查询口（建议签名，实现单定名）**：`versionChain(sessionKey, assetId): VersionChainEntry[]`
  （按窗口序升序；`{version: number|null, firstSeenRef, contentHash: string|null}`）。
- **幂等锚**：无（查询层不落库 ⇒ 无主键问题）。
- **63 三条判据逐条**：
  - ① 生产者：**S6 corrected 规则自身（本 spec）+ 既有 fetched 行** ⇒ ✓；
  - ② 语义定稿度：**本 spec §1.3 定稿** ⇒ ✓；
  - ③ 谁读：**L1 规则**（判定）+ 审计/回放（S7 展示层）⇒ 读者路径明确 ⇒ ✓ 三判据全过。

  超时/成本不可接受"⇒ 追加物化表提案（独立评审，不在本 spec 预建）。
- **与 F7 的一致性**：快照只覆盖**归档窗口**；锚版比较**不得回查当前存储**（DR-6a）。

## 4 `task_boundary` 启发式（判据 / 生产点 / 触发时机 / 收窄清单）

> **已裁定（见勘正 3 裁定 ②）**：结构信号优先（复用生产机制）；依据/反例保留供复核。
> 档源仅 `design :58`"任务边界精确化（任务结束/用户批准等触发规则）→ 50 spec"六个字
> （以下口径为推荐读法，依据 + 反例在下方）。

- **判据（可机械化，推荐 = 结构信号优先）**：
  1. **主信号（结构）**：**epoch 切换**——复用既有 compaction 语义（`decision-unit-runner.ts`
     `messageCount < watermark` ⇒ `message-increment-archive.ts` 的 **epoch+1 归零重放**）：
     **同一 session 的归档 epoch 递增 = 一个任务段结束、新任务段开始**（F9 实锤：机制已实现、
     验收装置已有）。
  2. **佐证信号（文本，既有模式）**：`user-query-extractor.ts:59` 的
     `[COMPACT/COMPACTION/… MODE:…]` 模式命中（**复用既有识别**，不新造词表）。
  3. **不采用**：自由文本"确认语"词表（"ok/thanks"类）——脆弱、无档源（62 的"不猜"纪律）。
- **语义（触发对象）**：`task_boundary` 是一种**入队触发源标记**（与 `decision_unit`/`manual`
  并列）：**在观测到任务边界信号时，对该任务段内的单元发起一轮判定入队**（`trigger="task_boundary"`，
  `round` 仍按 61 的账本 = **max+1**；判定内容不变，仅触发源变）。
- **生产点**：**入队侧**（`enqueueUnitsForJudge` 的调用方——runner 观测到 epoch 切换时）；
  不在 worker/S6 判定侧硬编码。
- **触发时机**：**epoch 切换被观测到的那一刻**（同会话、增量批次内）。
- **反例**：无 epoch 切换也无 `[COMPACT…]` 命中 ⇒ **不得产 `task_boundary`**（§16.3 的禁产在
  "无信号"场景下**继续成立**）。
- **收窄 §16.3 T4/R3 的动作清单**（实现单执行，逐条点名）：
  1. **§16.3 表格**：`task_boundary` 行补"生产点"列（= 本节的入队触发），"**禁产**"改为
     "**仅由边界信号产**"；
  2. **T4**（`rejudge.test.ts` 的"库内不含 task_boundary"）：**保留**当前场景断言（该场景无边界
     信号 ⇒ 仍不含），**新增正向格**：注入 epoch 切换 ⇒ 含 `task_boundary` 且 round=1；
  3. **R3**（"生产路径产 task_boundary ⇒ T4 红"）：语义改为"**无信号时产** ⇒ 红"（反向控制的
     目标从"绝对不可达"收窄为"无条件不可达"）；
  4. **§16.2 的 `--rejudge`** 不动（manual 语义不变）。

## 5 `asset_corrected` 写口设计（形状 / 幂等锚 / payload / §14 收窄清单）

- **形状**：复用 `attribution_status_events` 表（§14.1 既有 DDL；**不建新表**）——
  行 = `event_type="asset_corrected"`、`turn_seq`/`msg_seq` 恒 NULL（照 §14 纪律）、
  `asset_id` 恒非空（三路的输入都锚定具体资产）。
- **幂等锚（⚠️ 与 §14 的既有派生式存在硬冲突 —— 勘正处置；**已按勘正 3 对齐**）**：
  §14.1 的 `status_id = se_+sha1(unit_id|asset_id|round)`（**不含 event_type**）⇒ 同
  (unit_id, asset_id, round) 的 used 与 corrected **会撞主键**。**处置**（照 64 工单 F9"发现硬
  冲突 ⇒ 勘正 append，不改原行"，对齐口径见**勘正 3 ⑤**）：**派生式分公式**——
  `asset_used` 沿用**三元组** `se_+sha1(unit_id|asset_id|round)`（历史值与重放行为不变）；
  **corrected 用五元组** `se_+sha1(unit_id|asset_id|round|event_type|route)`（同 (unit,asset,round)
  的两条不同 route 的 corrected 不撞主键——与 §2.1 的唯一声明一致）；其余新事件型含 `event_type`
  （四元组兜底）。实现单须给"存量行兼容性实测（重放 ⇒ duplicate 且行数不变）"，并**同批在
  §14 勘正区 append**（不改 §14 原行）。
- **payload 链接字段**（只回指不复制，照 §14 F6 纪律）：
  `{ used_status_id（被修正行，三路必带）, judgement_id, correction_route: "version_drift"|"binding_revoked"|"unreachable", anchored_version?, latest_version?, source_asset_id?, binding_ref?, severity }`。
- **payload 新鲜度契约（对 S7 的强制约束；68 append）**：`anchored_version` / `latest_version` =
  **检测时（首次判定）快照**，**不是当前版本**。成因（引证，不许省略）：幂等锚不含版本
  （`status-events-repo.ts:113-121`：`base = unitId|assetId|round`；corrected = `base|eventType|route`
  五元组）+ 冲突时 `ON CONFLICT(status_id) DO UPDATE SET event_type = excluded.event_type`
